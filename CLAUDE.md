# aivideoeditor: working notes for agents

AI Video Editor is a Windows desktop video editor (egui) with the `ave`
command line under it, one Rust binary: index footage, plan beat-synced
edits, render and export timelines. `ave` with no subcommand opens the
editor; `ave index`, `ave plan` and the other subcommands run the same
engine headless, and `ave mcp` serves it to the assistant.

The project was generated by create-rust-app, and the rules below are the
ones its build enforces from the first commit. Keep them; they are cheaper
to keep than to restore.

## Commands

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo run                                       # the app, debug
cargo run --release                             # the app, as shipped
cargo deny check                                # licences, advisories, sources
cargo run --example changelog -- --check        # CHANGELOG.md matches the history
cargo run --example credits -- --check          # THIRD_PARTY.md matches Cargo.lock
```

`THIRD_PARTY.md` is generated: after a dependency change, run
`cargo run --example credits` and commit the result.

All of these are clean on `main` and enforced by CI
(`.github/workflows/ci.yml`). A warning is a build failure there.

## Editing video with `ave` (for agents)

**Do not judge footage by looking at frames or contact sheets.** You can't
watch video and you're bad at reading thumbnails; that's why this tool exists.
Read `<work>/shotlog.md`, plan from it, and when a judgment is missing, add a
signal to the index (a measurement in `analyze/`, a caption field in
`caption.rs`) instead of opening images. Whether an edit is better than the
human one is the human's call: render it and hand it over.

The loop: `index` → `caption` → `beats` → `people` (review the draft
as text, rename, add `clip@from-to` ranges) → `plan` → read the plan and the
shot-log lines of the segments it used → edit the TOML → `check` → `render` →
`otio`. Plans are the storyboard: every shot carries a `note` saying why it is
there. Never render a plan that fails `check` without saying so.

## Commit only what you changed

**This repository may be worked on by more than one agent at a time.**
Assume the working tree holds someone else's half-finished work, and check
`git status` before staging anything.

`git commit` commits the whole index, not just the paths you passed to
`git add`. Use `git commit -- path/to/file` so a staged change you did not
make cannot ride along. Never `git add -A`, never `git add .`, and never
`git commit -a`.

Commit subjects use the conventional prefixes `feat:`, `fix:`, `perf:`,
`refactor:`, `docs:`, `test:`, `build:`, `ci:`.

**Line endings are `.gitattributes`' problem, not yours.** Every text file
is stored and checked out as LF, including on Windows. Do not convert
endings by hand.

## Rules the build enforces

### Lints: no `unwrap`, `expect`, `panic!`, `todo!`, `unreachable!`, not even in tests

Denied in `[lints]` in `Cargo.toml`, so a violation is a build failure.
Use `?`, `let ... else`, or an explicit fallback. Tests return
`anyhow::Result<()>`, and every `assert!` carries a message. Release builds
use `panic = "abort"`, so a panic is a crash, not an unwound error.

The same block denies `wildcard_enum_match_arm` (name every variant: that
is what catches a new variant silently doing nothing), `missing_docs`,
`unreachable_pub`, and `allow_attributes`. Suppress with
`#[expect(lint, reason = "...")]`, never `#[allow]`: `expect` fails the
build when the lint stops firing, so a suppression cannot outlive the thing
it was suppressing.

### Unsafe Rust is a leaf boundary, without exceptions

- First try to remove the unsafe operation. Prefer safe standard-library
  APIs, checked slices, and RAII owners.
- Required unsafe code belongs only under `src/win/`. Everything else calls
  safe wrappers. `unsafe_code` is denied crate-wide in `Cargo.toml`, and
  `mod win` in `lib.rs` is the one `#[expect(unsafe_code, reason = ...)]`.
- Put each FFI call in its own small, named, private **safe** function.
  That leaf contains one unsafe operation and nothing else.
- Every unsafe operation needs an immediately relevant `// SAFETY:` proof.
- Do not expose `unsafe fn`. Never add unsafe to a test.
- Any resource with a matching close/free/destroy API gets one owning type
  whose `Drop` releases it exactly once.
- Never silence an unsafe lint any other way. `src/unsafe_check.rs` fails
  the build for unsafe outside `src/win/`, in a test, as an `unsafe fn`, or
  twice in one function.

### A discarded result says why

Outside tests, `let _ = f();` and a trailing `f().ok();` carry a `//`
comment, on the line or directly above it, saying why there is nothing
to do with the failure (a send to a thread that has gone, best-effort
cleanup). `src/discarded_check.rs` fails the build otherwise. `write!` and
`writeln!` are exempt. If you cannot write an honest reason, handle the
error.

### Parsers of outside input have property tests

`people.toml` keys, `recipe.toml`, plan files and MCP messages come from
people and other programs. Each parser has a `proptest` property (any
input: no panic, and the invariants the rest of the code relies on). A new
parser of outside input gets one too.

### Every source file opens with the header banner

A ruled block naming `Module:`, `Description:` and `Dependencies:`, then a
blank line, then the module's `//!` docs:

```rust
// ============================================================================
// Module:       config
// Description:  Loads and saves the user's settings.
//
// Dependencies: serde, toml
// ============================================================================

//! The config file: every field optional, parsed independently.
```

`src/header_check.rs` walks `src/`, `tests/` and `examples/` and fails the
build for a file missing one, so a new file needs its header in the same
commit that adds it. `Module:` is checked against the path the file sits at:
`src/foo/mod.rs` is `foo`, `src/lib.rs` is `aivideoeditor (library crate root)`,
and `tests/x.rs` is `x (integration test)`.
Copy an existing header and fix all three fields. The banner is plain `//`,
not `//!`; the reasoning belongs in the `//!` block below it.

### The toolchain is pinned, once

`rust-toolchain.toml` pins `1.99.1`, and every workflow's
`toolchain: "..."` line must name the same version;
`tests/toolchain_pin.rs` fails the build if they drift. Bump them together,
in their own commit. Never `@stable`: CI would move to each new release on
its own, and a lint that does not exist locally cannot be caught locally.

### Workflows are pinned, locked and timed

`tests/workflow_hygiene.rs` fails the build for a workflow that uses an
action by tag instead of a full commit SHA with a `# vX.Y.Z` comment, has
no top-level `permissions:`, runs a resolving cargo command (`build`,
`check`, `clippy`, `doc`, `install`, `metadata`, `run`, `test`) without
`--locked`, or has a job without `timeout-minutes:`.

### Every dependency passes `cargo deny check`

`deny.toml` allows a fixed list of permissive licences, denies unknown
registries and git sources, and fails on known advisories. Adding a crate
under a licence not on the list is a decision, not a fix: add it to
`deny.toml` in its own commit, saying why. An ignored advisory carries a
note saying what would clear it.

### `CHANGELOG.md` is generated from the commit subjects

Do not hand-edit its lists. `cargo run --example changelog` rebuilds it
from the conventional-commit subjects in the git history (`feat:` under
Added, `fix:` under Fixed), and CI runs it with `--check`, so the subject
*is* the changelog entry: write it for a user. Before a release,
`cargo run --example changelog -- --release vX.Y.Z` writes the section
for the tag about to be cut; a paragraph between that heading and its
first `### ` is the release's summary, kept on every regeneration and
published as the release notes. A pushed subject that is wrong is
corrected in `CHANGELOG.corrections` (`<full hash> <subject>`), never by
rewriting history. v0.1.0 predates the generator and keeps its
hand-written section (`PRE_GENERATOR` in `examples/changelog.rs`).
**Never amend or rebase a commit after tagging it.**

### Constants live with what they govern

There is no `constants.rs`. Use a function-local `const` first, then a
module-private one, then `pub` in the module that owns the concept.

## Things that are deliberate, not oversights

- **`panic = "abort"` and fat LTO in `release`.** Smaller, faster binaries;
  `release-fast` is the profile for iterating.
- **`main.rs` is a thin shell over `lib.rs`.** The logic lives in the
  library so tests and examples reach it without spawning a process.
- **Exit code 2 for refused arguments.** That is the convention shells and
  scripts expect from a usage error, distinct from a runtime failure.
- **Every config field is optional and parsed on its own.** One bad value
  costs that setting, not the file, and writes go through a temp file and a
  rename so a crash mid-write cannot leave a half-written config.
- **Dependabot groups patch bumps only.** Under cargo a `0.x` minor bump is
  the breaking one, so it arrives as its own PR.
- **Actions are pinned to full commit SHAs**, with the version in a trailing
  comment. A mutable tag is a supply-chain risk; a pin moves in a reviewed
  diff.
